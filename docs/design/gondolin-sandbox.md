# Gondolin micro-VM sandboxes (opt-in)

Status: built on the branch `feat/gondolin-sandbox`. Tanner answered the open decisions with the recommended choices: **the browser inside the VM (option A)**, with no browser when the image has none, and never the host browser in a sandboxed session; **network: allow list by default**; **the folder read and write, with `.git/config` and hooks protected**; **only the owner chooses by default** (the owner may allow guests who steer); **Gondolin is not a dependency**: Set up installs it into `<data>/gondolin`; and **no image is hosted or published**: Set up with a browser builds it on the person's machine.

Pi Pocket runs Pi's commands on the machine, as the user who started the server. This feature adds an **option**: a session can run its file and shell tools inside a local Linux micro-VM, made by [Gondolin](https://github.com/earendil-works/gondolin) 0.14. It is off by default. The owner turns it on, and a session uses it only when someone chooses it for that session.

## What Gondolin gives us (checked)

- A VM per session, on Linux and macOS only. Two back ends:
    - **`krun`** (libkrun). A prebuilt runner comes in an optional npm package for `linux-x64` and `darwin-arm64`. Linux needs read and write access to `/dev/kvm`. This is the one that **ran on this machine** (no QEMU is installed here).
    - **QEMU**, the upstream default. It needs `qemu-system-x86_64` or `qemu-system-aarch64` on `PATH`, with KVM (Linux) or HVF (macOS).
- **Windows has no Gondolin support.** Windows people use Pi Pocket inside WSL2 (Linux support applies if the WSL2 kernel has KVM).
- A guest image of about 200 MB (325 MB on disk, unpacked), downloaded once from GitHub releases into an image store. Alpine Linux, with `bash`, `sh`, `curl`, `node`, `npm`, `python3`, `find`, `grep`, `sed`, `awk`, `tar`. **Not in it: `git`, `rg`, `make`, compilers.** A custom image (`gondolin build`) can add them.
- Its disk is 270 MB with 80 MB free by default. The VM option `rootfs.size` makes it larger.
- A host folder mounts into the guest through a FUSE bridge. The mount path in the guest can be any path. **We mount the session's folder at its host path** (for example `/home/me/app` in the VM is `/home/me/app` on the host), so paths in the transcript, in `AGENTS.md`, and in tool results stay true. Gondolin's `RealFSProvider` refuses symlinks that leave the folder. A symlink inside the guest is resolved by the guest, not the host.
- Network: the guest has no route to the host's `localhost`, and none to private ranges (`192.168.x.x`, `169.254.169.254`, `10.x`): the proxy answers 403. Public HTTP and HTTPS go through Gondolin's proxy, which can limit hosts (`allowedHosts`), and can hold secrets outside the guest.
- Ingress is HTTP only, by path prefix, on one host TCP listener. We do not use it (see D4).

## Decisions

### D1. Where it lives: core mechanism, extension workflow

Rule C7 of [core or extension](../extensions/policies/core-or-extension.md): split it.

**Core** (small, `src/server/sandbox.ts`, with a few lines in `app.ts`, `commands.ts`, `subagents.ts`, `linked-sessions.ts`, `host.ts`). It has what an extension cannot keep safe (C1, C2, C4):

1. **The setting of a session.** A new document kind, `pocket.sandbox` (`{ on, by, at }`, conversation scope, `latest`, fork `current`). It is stored data, so a session stays sandboxed across restarts, forks, subagents, and linked sessions. Only a new kind is added; no existing kind changes.
2. **Fail closed.** If a session is sandboxed and no sandbox module is on, or it cannot start the VM, every file and shell call of the session fails with a clear message. **Core never runs a sandboxed session's tool on the host.** An env that fails for each call replaces the host env.
3. **The tool gate.** A `beforeTool` hook in `pocket-core` (the hook that is already there) blocks tools that would reach the host from a sandboxed session (see D3).
4. **Who may.** `host.sandbox.set` checks that the person can drive the session, and asks the module whether they may choose a sandbox (D6).
5. **The extension point** `host.sandbox` (experimental, since 0.31.0): `register(provider)`, `get(conversationId)`, `set(conversationId, on, user)`. It has a first user (the module below), as rule C15 asks.

**Built-in extension `pocket-gondolin`** (`src/server/extensions/gondolin.ts` and `gondolin/`). It is off by default (`OFF_BY_DEFAULT`). It holds the workflow: the VM driver, the execution environment, the lifecycle, settings, routes, and the browser module (the indicator, the sheet). At run time it uses `host` and `web` only (C14).

### D2. What runs in the VM

All of Pi's execution environment, because Pi Durable's tools reach files and processes only through `ExecutionEnv`:

| Runs in the VM                                                     | Why                                            |
| ------------------------------------------------------------------ | ---------------------------------------------- |
| `bash`, `read`, `write`, `edit`                                    | Pi's four tools use the environment            |
| `!` commands in the message box                                    | `shell.ts` uses the environment                |
| The check of a "Done when" goal                                    | `goals.ts` uses the environment                |
| `codemode` scripts' calls to these tools                           | They go through the same tools                 |
| Subagents of the session (they share the session's VM)             | A subagent's conversation inherits the setting |
| Linked sessions the sandboxed session starts (each has its own VM) | They inherit the setting: no way out           |

### D3. What stays on the host (and the UI says so)

| Tool or feature                                                                                                              | In a sandboxed session                                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`browser` tool and the Browser panel**                                                                                     | Run **in the VM** (Chromium in the guest, the image with a browser). **Without** that image: no browser. The host browser is never used for a sandboxed session. |
| Files, Changes, Git panels, uploads, the file viewer                                                                         | Run on the host and read the shared folder. They are for people, not for Pi.                                                                                     |
| `ask`, `ui`, `memory`, `schedule`, `tool_search`, `subagent`, `codemode`, plan and goal tools                                | Allowed. They change Pi Pocket's own state only, or they pass through the gate again.                                                                            |
| `artifact` with `content` or `edits`                                                                                         | Allowed. With `path` it reads a host file, so it is blocked.                                                                                                     |
| **`background`** (host processes that outlive a call)                                                                        | **Blocked by default.** A host shell is the way out of the VM.                                                                                                   |
| Session tools (`session_start`, `session_send`, `team`, …), `design_*` tools, `watch_pr`, MCP tools, other extensions' tools | **Blocked by default**: they run on the host or start work on the host.                                                                                          |

The owner can change the blocked row with the module's setting **Host tools in sandboxed sessions: Block (default) or Allow**. A tool that is not in the lists above counts as a host tool. This is an allow list, so a new tool is blocked until someone classifies it. The sheet lists, with words, what runs where.

The pattern: **the browser runs inside the same boundary as the code it tests**, and the human watches a stream (VNC or a screencast) through the product's own authenticated channel. Publishing a port is an extra, authenticated step (a token, a signed URL, private by default). None of them points an unrestricted host browser at a sandbox's code.

**Two options for Pi Pocket, measured on this machine** (real Gondolin VM, krun, KVM, 2 CPUs; medians of 3 runs):

- **A. Chromium inside the VM.** Pi Pocket's browser layer already speaks CDP over a pipe (`--remote-debugging-pipe`, fd 3 and 4: `src/server/browser/cdp.ts`). In the VM the same pipe runs through `vm.exec` stdin and stdout (`exec chromium … 3<&0 4>&1 1>&2`). Only the host controls that channel; there is no listener. The Browser panel keeps its screencast. The guest reaches its own dev server at `localhost:5173`, and HTML files in the shared folder at their host path (`file:///…`). The network rules of the sandbox cover the page (allow list), so a page cannot reach the host's `localhost` or LAN. Cost: image +280 MB download (110 → 392 MB) and +860 MB on disk (325 MB → 1.2 GB); first tool call 401 → 672 ms; Chromium up with `about:blank` 1.2 s; a local file loads in 51 ms (warm 38 ms); +193 MB guest RAM idle, +205 MB with a page; host RSS +410 MB. HTTPS needs the sandbox's CA in Chromium's NSS store (`certutil`, 0.6 s, tested). Work: a launcher for the in-VM Chromium behind the existing browser layer, a per-session choice of launcher in core (small), and the image. The image is the hard part: Gondolin 0.14's `gondolin build` makes a krun image that does not boot here, so we need an upstream Chromium image or our own release asset.
- **B. Host browser, routed into the VM.** Chromium's per-context proxy takes only `http`, `https`, `socks4`, `socks5` addresses ([proxy docs](https://chromium.googlesource.com/chromium/src/+/main/net/docs/proxy.md)): a proxy that reaches the guest needs a **host TCP listener** (rejected). The only listener-free route is the CDP `Fetch` domain (Pi Pocket answers each request from the guest through `exec`): `Fetch.fulfillRequest` takes a whole body, so there is no streaming, no WebSocket, no hot reload, and every request costs an `exec`. And it does **not** confine anything: the page's JavaScript runs in a host process with the host's network (`localhost` services, the LAN), so code that the model wrote runs next to the host's services. That breaks the boundary that the sandbox exists to hold.
- **C. No browser in sandboxed sessions** (what Codex cloud does). Simple and safe; Pi loses visual checks of UI work. HTML files can still be opened by a person in the Files panel.

**Recommendation: A, as an option inside the option, with C as the fallback.** Setting **Browser in sandboxed sessions: In the sandbox (needs the image With browser) / Off**. Default: In the sandbox; a standard image has no browser, so the tool and panel say so. **Never the host browser** in a sandboxed session (the tool says why). Set up offers **Set up** (the standard image, 110 MB) and **Set up with a browser** (a second image, about 390 MB, built here). The UI says "Browser runs in the sandbox, with the sandbox's network rules" and the Browser panel shows the in-VM page. People who want the host's own browser start a session without a sandbox. **Costs of A:** about +280 MB download, +0.3 s first call, +1.2 s for the first browser use, +205 MB RAM per VM that opens a page, and the work above. **Decided (built):** A, with C when the image has no Chromium; the image is built on the person's machine by Set up with a browser (the size and time are shown before it starts), and kept apart from the standard image.

### D5. The mount, the network, secrets

- **Mount:** the session's folder, **read-write** by default (the folder is the work product), at its host path. Setting **Mount: read-write or read-only**. Read-only gives a VM that can run and read, and cannot change the folder (use with a scratch folder in `/tmp` inside the VM). A copy-on-write mount is **out of scope**: Gondolin 0.14 has no overlay provider (`ShadowProvider` hides files, it does not overlay).
- **Protected paths inside a read-write mount.** The guest cannot write `.git/config`, `.git/hooks/`, `.git/info/`, `.gitmodules`, `.git/modules/*/config`, and `.gitattributes`. Reason: Pi Pocket's Changes panel and the owner's own `git` commands run on the host. A hook or `core.fsmonitor` that the VM wrote would run there, outside the VM. The VM reads these files. A write fails with `EACCES`.
- **Uploads.** The session's own upload folder mounts **read-only** at its host path, so Pi can read what a person attached.
- **Nothing else of the host mounts.** Not `~/.pi/agent`, not `~/.pi-pocket`, not `~/.ssh`, not the home folder. The VM has its own `/root`.
- **Environment:** the VM gets none of the server's variables. Variables that `host.commandEnv` adds to host commands are **not** added in a sandboxed session (they are secrets for host commands). Values that extensions hide still leave all output.
- **Network.** Setting **Network: Off, Allow list (default), or Open**. Off: no network device. Allow list: the hosts in the list (default: package registries and GitHub: `registry.npmjs.org`, `*.npmjs.org`, `registry.yarnpkg.com`, `pypi.org`, `files.pythonhosted.org`, `crates.io`, `static.crates.io`, `index.crates.io`, `proxy.golang.org`, `rubygems.org`, `github.com`, `*.github.com`, `*.githubusercontent.com`, `dl-cdn.alpinelinux.org`). Open: any public HTTP or HTTPS host. In all modes the proxy blocks private and local addresses (this is Gondolin's own check, which we kept on), and no SSH or raw TCP leaves the VM. The owner edits the list.
- **No secrets enter the VM**, and the module's code has no path that adds one. A person who types a secret into a command still puts it in the VM: that is theirs to decide.

### D6. Who may turn it on

- **The owner** turns the module on (Menu → Extensions). It is off by default.
- **Choosing it for a session:** the owner always. People who can steer a session only when the owner turns on **Let people who steer choose** (off by default). Viewers and people invited to one session never can (extension routes are closed to them, and core checks the session).
- **Turning it off for a session:** the same rule. A guest cannot take a sandbox away that the owner set (`by` is stored; only the owner can remove a sandbox that the owner chose).
- **New sessions:** the setting **New sessions start in the sandbox** (off by default). Core applies it in the commit that creates the session, so no first message can run on the host in between.

### D7. Lifecycle

- **One VM per session** (subagents share it). **Start:** on the first tool call, never at module load. The call waits (about 1 to 3 seconds; the first one after set-up downloads nothing). **Stop:** after **idle minutes** (default 30, 0 for never) with no call running (and no browser page open); when the session is archived or removed; when the module goes off; when the server stops.
- **A stopped VM keeps nothing.** Files that the VM made outside the folder go. Files in the folder stay (they are on the host). Processes in the VM end. The sheet says so.
- **Limits:** **CPUs** (default 2), **memory** (default 2 GB), **disk** (the VM's root disk, default 4 GB, thin), **Most sandboxes at once** (default 3). A fourth session gets a visible failure ("3 sandboxes already run: stop one or raise the limit"). Each command also has Pi's own timeout.
- **Restart of the server:** the VMs end with the server (they are its child processes). A tool call that the restart cut off comes back as **interrupted** and is never replayed: Pi's `bash`, `write`, and `edit` are not replay-safe, and this feature does not change that. The next call starts a new VM. A process that wrote a pid file (`pi-pocket/gondolin/vms.json`) lets the next start remove a runner that a crash left behind: it checks the process's command line before it ends it.
- **Cleanup:** VM disks live in the system's temp folder and go when the VM stops (`rootDiskDeleteOnClose`). The image store is in `<data>/gondolin/images`, owned by the module; **Remove image** in the sheet deletes it.

**Known issue (Gondolin 0.14.0):** `gondolin build` makes a libkrun image that does not boot on x86-64 Linux ("Kernel doesn't fit in RAM": the built `krun-kernel` is not the published one). Set up with a browser works around it: it runs `buildAssets` with the Chromium packages added, takes only the new `rootfs.ext4`, puts it into a copy of the published image's directory (kernel, initrd, krun files), patches the manifest's checksum and build id, and imports it as `pocket-browser:latest`. The Linux build uses the host's `mke2fs`, `cpio`, `lz4`; macOS needs Docker or Podman for it (Gondolin's own rule). It was run here: 35 s for the build, and the browser ran in the VM (a file of the folder, the VM's own `localhost` server, an allowed HTTPS site; not the host's servers).

### D8. Set-up and failure

- **Nothing downloads without a tap.** Menu → Extensions → Gondolin → **Set up** (owner only) does two things: it installs the package `@earendil-works/gondolin@0.14.0` into `<data>/gondolin/` (`npm install --ignore-scripts`, nothing global, no system change), and it fetches the guest image into the image store (Gondolin checks its SHA-256). Pi Pocket gets no new dependency, and nobody pays 50 MB for an option that they do not use.
- **Check** (the sheet shows it, and the module's route answers it): operating system; Node 22.19 or newer; the package; the back end (krun runner present with KVM or macOS arm64, or QEMU on `PATH`) with the reason when not; `/dev/kvm` access on Linux; the image; free disk. Each line is "ok" or says what to do (for example: "QEMU is not installed: `sudo apt install qemu-system-x86` on Debian, or `brew install qemu` on macOS. Pi Pocket does not install system packages.").
- **A call that cannot start the VM fails** with the reason, in the tool result Pi gets and in the transcript: "Sandbox could not start: …". There is **no fallback to the host**, ever. The module records the last start error, and the sheet shows it.
- **Choosing a sandbox for a session** while the check fails is refused with the same words (the owner can still fix it first).

### D9. UI

- **Status line:** a status item `Sandbox` on every sandboxed session, with the state (`starting`, `running`, `stopped (starts on next use)`, `error`). Tapping it opens the sandbox sheet. It is a real button, 44 px high on a phone.
- **Session menu row:** "Run this session's tools in a sandbox" (a switch). It shows only to people who may choose.
- **The sheet** (`sandbox` in the browser module): the state; **what runs where** (the table of D2 and D3); the mounted folder and its mode; the network mode and list; CPU and memory; the last error; buttons: **Stop VM**, **Start VM**, **Check**.
- **Settings** (Menu → Extensions → Gondolin, owner only; declared with `web.settings`): backend, mount, network, allow list, browser (after D4 is approved), CPUs, memory, disk, idle minutes, most at once, host tools, let people who steer choose, new sessions start in the sandbox, image.
- **A prompt note** (core, one short section while the session is sandboxed): "Your tools run in a sandbox (a Linux VM). The folder is mounted at its usual path. Host files elsewhere are not there. Servers that you start listen inside the sandbox only."

### D10. Threat model

**Protects against** a mistake or a prompt injection in Pi's commands harming the host _outside the session's folder_: reading `~/.ssh`, `~/.pi/agent` sign-ins, `config.json` and its token, other sessions' folders; running a process on the host; reaching the host's local network or `localhost` services; sending data to a host that is not on the allow list.

**Does not protect against:**

- Anything in the mounted folder: Pi can read every file in it (including `.env`) and change them (read-write). A backdoor in your source stays a backdoor. Protected paths (D5) cover only the host's own git use.
- A vulnerability in Gondolin, in its host-side file bridge or network proxy (they run inside the Pi Pocket server process, in TypeScript), in libkrun or QEMU, or in the guest kernel. This is a VM, not a proof.
- The tools that stay on the host (D3). Browser pages are code from Pi that the host browser runs.
- Data that leaves through an allowed host (the registries, GitHub). The Open mode lets it leave to any public host.
- Time-of-check races between the host-side path checks and the host file system (hard links, swaps by another process on the host).
- People: anyone who can steer can already do what the owner does with Pi. The sandbox limits Pi, not people; owner-only settings stay owner-only.
- A resource attack on the host's CPU or disk beyond the limits above (the limits are best effort).

## Out of scope

Copy-on-write mounts; snapshots that survive a restart; a sandbox for the whole Pi Pocket process (Docker does that: [docker.md](../docker.md)); Windows without WSL2; extra mounts chosen by people; secret injection into the VM (Gondolin can do it, we do not offer it); routing the `background` tool into the VM (a later change); a per-folder rule; a sandboxed git worktree session's `.git` link (the worktree's `.git` file names a path outside the folder, so `git` in the VM does not find its repository: use the session's folder, or run git on the host); sandboxed sessions of a remote workspace (`ssh://`): refused.

## Tests

Gondolin runs behind a `SandboxDriver` interface. Tests use a fake driver (a temp folder as the guest, a real shell for `exec`, and this machine's Chromium for the browser's DevTools pipe), Pi Durable's env conformance cases for the guest environment, and an opt-in file (`test/gondolin-real.test.ts`, `PI_POCKET_GONDOLIN_REAL=<folder with the package>`) that runs the real driver: it skips without KVM or QEMU, the package, and the images. The PR says what ran.
