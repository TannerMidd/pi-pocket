# Sandboxes: running a session's tools in a micro-VM

By default, Pi's commands run on the machine where Pi Pocket runs, as the user who started it. A **sandbox** is an option that moves a session's tools into a small Linux virtual machine on the same machine, made by [Gondolin](https://github.com/earendil-works/gondolin). **It runs on Linux only for now**: on macOS and Windows the check says "The sandbox runs on Linux only for now.", Set up is not offered, and no session can be put in a sandbox. It is off until the owner turns it on, and a session uses it only when someone chooses it for that session.

A sandbox limits what a mistake, or a prompt injection that Pi reads, can do to the rest of the machine. It is not a proof: [what it protects](#what-it-protects-and-what-it-does-not) says what it does not.

## Turn it on

1. **Menu → Extensions → Gondolin sandbox**: turn it on. The owner does this. A new profile has it off.
2. Open the module's entry in the same sheet and tap **Sandbox set up** (under **Open**), or press Ctrl+K and type `sandbox`. This works with no session open, for the owner only. The Sandbox sheet opens, with **Set up** in its **This machine** part. The sheet says what it will do before it starts:
    - It installs the package `@earendil-works/gondolin` (0.14.0) into the `gondolin` folder of Pi Pocket's data folder. Nothing global, nothing outside that folder. It uses `npm install --ignore-scripts`.
    - It downloads the guest image into the same folder: about 110 MB (325 MB on disk), and then **builds the standard image with `git`** on this machine from it (about 10 seconds, 11 MB more on disk, 336 MB in all). It needs `mke2fs`, `cpio`, and `lz4`; without them Set up says so and the sandbox works without git in the VM.
    - **Set up with a browser** also builds a second image with Chromium (and git) on this machine: about 250 MB of packages, 1.2 GB on disk, a minute or two. Pi Pocket publishes no image: the images are made here. Without it, a sandboxed session has no browser.
3. Choose a session's sandbox: **Menu → Sandbox** in the session (in **This session**, with Rename and Pin) (or the **Sandbox** item in its status line once it is on). The owner always may. It is refused, with the reason, while the session still runs work on this machine (a background task, a `!` command, or a file or shell call in the middle of a run): stop it or let it end first, because a sandbox cannot take it over. Guests who steer may only when the owner turns on **People who steer may choose the sandbox**. Viewers, and people invited to one session, never.

**New sessions start in the sandbox** is a setting too (off by default).

## What runs where

| Runs in the VM                                                                                   | Stays on this machine                                                                    |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `read`, `write`, `edit`, `bash`; `!` commands; the check of Done when                            | Files, Changes, and the file viewer (they read the shared folder, for people)            |
| Calls that `codemode` and subagents make to those tools                                          | `ask`, `ui`, `memory`, `schedule`, `tool_search`: they change only Pi Pocket's own state |
| The browser: **a Chromium inside the VM** (the image with a browser)                             | Everything else is a **host tool** and is **blocked** by default (below)                 |
| `background` tasks: their processes run in the VM ([below](#background-tasks))                   |                                                                                          |
| `team` (start, send, list): the linked session is sandboxed too ([below](#linked-sessions-team)) |                                                                                          |

**Host tools** are tools that would run on this machine, outside the VM: session tools (`session_start`, …), design tools, `watch_pr`, MCP tools, other extensions' tools, and `artifact` with a `path` (its own, or an asset's). A sandboxed session cannot use them, because they would be a way out. The owner can allow them (**Host tools in sandboxed sessions**). A tool that Pi Pocket does not know is a host tool, so a new tool is blocked until it is listed.

### Background tasks

In a sandboxed session the `background` tool (start, output, list, jobs, stop) runs its commands **in the session's VM**, never on this machine. Output is captured, a task that prints nothing for its limit is stopped, Pi gets a message when one ends, and a stop ends the process in the guest. The VM **stays up** while a task runs (no idle stop). A server that a task starts is reached by the browser in the sandbox at `localhost:<port>`; Pi Pocket opens no port on this machine for it.

What a restart does: **the VM ends with the server, so the task ends**. Pi is told "ended: the server restarted", never "resumed", and the task has to be started again. The same holds when you stop the VM from the sheet, or the module goes off. Resuming a job (`jobId`, `expectedAttempt`) is not available in a sandbox. Tasks are listed by the tool in this session only; the Running now list is for tasks on this machine.

### Linked sessions (team)

A linked session that a sandboxed session starts with `team` is **sandboxed too**, with the parent's settings, in **its own VM**, in the parent's folder. `team start` with a `cwd` outside the parent's folder is refused with the reason, unless the owner turns on **Linked sessions may use other folders** (the child is still sandboxed, and a folder with sign-ins or keys is never allowed). A sandboxed session can message (`team send`) only sandboxed linked sessions and the session that started it, because a message to a session that runs on this machine would be work there. Each linked session takes one of the **Sandboxes at once**.

The sandbox sheet (tap **Sandbox**) shows this table, the state of the VM, and the settings that apply.

## What the VM sees

- **The session's folder**, at the same path as on the host, read and write by default (**The session's folder**: read only is a choice). A file that Pi writes there is on the host at once.
- **Git follows its own trust model: the work tree is the guest's, and no git directory is.** A cloned repository is untrusted, and the repository's own files are trusted: so the VM writes the folder, and every git directory is read only to it. These are the repository's `.git` (or the folder that a `.git` file names, as `git init --separate-git-dir` makes it), the main repository's `.git` of a linked worktree (mounted at its host path; only that folder, not the main repository's working files), and the git directory of each submodule. A git directory outside the folder is a read only mount, whatever the setting of the folder. Inside the folder, writes into it fail with `EROFS`, whatever path they take: a link, a hard link, a rename of the folder that holds it. The VM also cannot create, change, rename, or remove any entry named `.git`, anywhere in the folder, in the spellings that Git itself treats alike (any case, trailing dots and spaces, `git~1`, and the invisible characters that HFS+ ignores).
- **So `status`, `diff`, `log`, `show`, `blame`, and every other read work in the VM, and every command that writes the repository fails**: `add`, `commit`, `branch`, `tag`, `checkout`, `switch`, `reset`, `stash`, `merge`, `rebase`, `config`, `remote`, `worktree`, `submodule`, `init`, `clone`, and `gc`. They fail with "pi-pocket sandbox: Git metadata is read only here. Ask the person to commit (or change branches, config, remotes) on the host." Pi edits the files, and you commit on the host. Git does not write its index in the VM when it only reads (`GIT_OPTIONAL_LOCKS=0`). The guest has its own git settings (`/etc/gitconfig`): the mounted folders are trusted (`safe.directory`), and the author is "Pi (sandbox)".
- **No credentials enter the VM**, so `git push`, and `git fetch` from a private repository, fail with "this sandbox has no credentials … from the host": **push from the host**.
- **A folder where git would run code from the work tree does not start read and write.** Git runs hooks and programs, and reads configuration, with your rights, on this machine. When a VM starts with the folder read and write, Pi Pocket asks git (`git rev-parse --git-path hooks`, `git config --list --show-origin --show-scope`), for the folder's repository and for every repository found below it, and refuses to start in these cases. The message names the path or the key:
    - **A place where the VM can write is in the way of what git runs or reads.** That is the hooks folder, a hook in it (`*.sample` files are not run), a file that git reads as configuration, or a file that one includes (`include.path`, `includeIf`, also one that does not exist yet), when it lies in the folder or is reached through a place in it (outside the git directories): a link that leads in counts, and so does a link in the folder in the middle of a chain that ends outside. A folder that holds a git directory cannot be moved by the VM, so it does not count. A husky repository (`core.hooksPath = .husky/_`) is such a case. Two rules do not depend on what git lists: **any link inside a git directory** (also a bare repository's, a submodule's, and the one above the folder) that leads into the folder, or through it, refuses, whatever file it is (`config`, `config.worktree`, a hook, `info/exclude`); and **every file that git reads as configuration is checked by its path, whether it exists or not and also when it is empty** (the repository's `config` and `config.worktree`, `~/.config/git/config` or `$XDG_CONFIG_HOME/git/config`, `~/.gitconfig`, and `/etc/gitconfig`), because git lists no value of an empty file.
    - **The repository's own configuration (local or worktree scope) sets a key that is not on a short list of plain data.** The list: `core.repositoryformatversion`, `filemode`, `bare`, `logallrefupdates`, `ignorecase`, `precomposeunicode`, `symlinks`, `autocrlf`, `eol`, and `worktree` (what git writes when it makes or clones a repository, and a work tree and a line-ending choice); `remote.<name>.url`, `pushurl`, and `fetch` (where a remote is); `branch.<name>.remote`, `pushremote`, `merge`, `mergeoptions`, `rebase`, and `description` (a branch's upstream); `user.*` (name, email, signing key); `extensions.*`; `init.defaultBranch`, `pull.rebase`, `push.default`, and `fetch.prune` (choices); `lfs.repositoryformatversion`; `submodule.active` and `submodule.<name>.url` and `active`. These are values that git-config's documentation describes as data, never a program or a file to read. **Every other key refuses**, `include.path` and `includeIf` too: a list of what to forbid kept missing keys (`pager.<command>`, `core.gitProxy`, `interactive.diffFilter`, `gpg.ssh.defaultKeyCommand`), so the list says what is allowed. Your global and system configuration are the machine's own, and any key may be there. A repository set up with `git lfs install --local` has `filter.lfs.*`, and a VS Code repository may have `branch.<name>.vscode-merge-base`: both need a read only folder (or `git lfs install` without `--local`).

    The repository **above** the folder counts too: a session in `/project/src` is checked against the configuration of the repository in `/project`. The machine's own configuration counts also when the folder holds no repository (a global or system file that includes a file of the folder). If git cannot be asked, or does not say the scope of a value, or a folder below cannot be read (so that a git directory in it would not be known), the VM does not start either. **A read only sandbox folder still works** in all these cases (the VM reads the hooks and the files and cannot change them), and a repository with husky can use the sandbox only read only, unless the hooks folder is in your global configuration and outside the project. A change to the configuration, or a repository that you create on the host, while the VM runs is not seen until the VM starts again. Every repository counts, each with its own git directory: the folder's, those below it (a bare repository too: a push into it on the host runs its hooks), and the one above. An included name is read as git expands it (`~/`, `~user/`, an absolute name, or a name relative to the file that includes it, with every `..` kept for the walk of links); a form that cannot be expanded the same way (`%(prefix)/`, an unknown user) refuses. Host Git runs for this check with the server's environment minus every `GIT_*` variable, the same as Pi Pocket's own git runs, so one environment policy decides both what is checked and what runs.

- **A folder that is, or lies inside, a git directory cannot be a sandbox's folder** (`.git`, `.git/hooks`, a bare repository): the VM would write the repository's own configuration and hooks. Choosing it is refused, with the reason, beside the private-folder check.
- **A file that has other hard links is not changed in place** in a read and write folder: opening it for writing, truncating it, and `chmod` fail with `EPERM`. The other names of it may be outside the folder (a package manager's store) or in a git directory. The VM can still replace such a file (write a new one and rename it over, which is what an editor does) or remove it. So an install in the VM that hard-links its files, and then writes into them, fails.
- **A bare repository that the VM builds inside the folder is not blocked.** The VM can write a folder that looks like a git directory (`HEAD`, `objects/`, `refs/`, `config`, `hooks/`, with no `.git` name), and your own git would run its configuration if you ran git inside that folder with git's default `safe.bareRepository = all`. A bare repository that is already in the folder when the VM starts is found and read only. Pi Pocket's own git is pinned to `explicit`. No rule that is both sound and harmless can stop a new one: it would have to refuse every file named `HEAD`, `objects`, or `refs` in the project. For your own git on the host, run once: `git config --global safe.bareRepository explicit`. Pi Pocket does not change your configuration.
- **The session's own uploads**, read only.
- **The skills the session uses**, read only, each at its own path (for example `~/.pi/agent/skills/<name>`, `~/.agents/skills/<name>`): Pi reads their `SKILL.md` with `read`. The list is fixed when the VM starts (**Stop** in the sheet and the next call picks up new ones).
- **Nothing else**: not `~/.pi/agent` (sign-ins), not Pi Pocket's data folder or its token, not `~/.ssh`, not your home folder. **A folder that is, holds, or lies inside** your home folder, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.pi`, `~/.pi-pocket` (or the data folder), `~/.config`, `~/.kube`, `~/.docker`, and similar private places **cannot be a sandbox's folder**: choosing the sandbox is refused, and a session that already has it fails each call with the reason. A project in the home folder is fine. **A folder that is, holds, or lies inside Pi Pocket's own install folder (the checkout or the package), the data folder (except its `worktrees/`), or the folders of drop-in extensions and themes cannot be a sandbox's folder either, in any mode, read only too**: Pi Pocket reloads its code from them while it runs, so a guest that could write there would run code as the server. Core refuses it (`reloadedFolderProblem` in `src/server/sandbox.ts`). The VM has its own `/root` and its own variables: none of the server's, and none that extensions add to host commands.
- **The folder of a sandboxed session is untrusted, as a cloned repository is.** The guest may leave a link in it, and may swap a folder for a link at any moment, so Pi Pocket never checks a path and then uses it. What it reads or writes on this machine in such a folder (the Files list and viewer, folder listings, `@` mentions, downloads and images, the relay's files in and out, `AGENTS.md` and `CLAUDE.md`, prompt templates, project skills, **Undo in Changes**, and the new files that a worktree copies) goes by a walk of the names, from the folder's own descriptor, that opens each name without following a link (`src/server/confined.ts`; on Linux, `/proc/self/fd/<dir>/<name>`). **A link anywhere on the way fails the call**: in the viewer, `AGENTS.md -> ~/.ssh/id_rsa` and a link to a file inside the folder alike say the path "passes through a link, which is not followed in this folder", and the prompt leaves such a file out and says so. On a system without that primitive the call fails with a message and never falls back to the path. **This applies only while a sandboxed session uses the folder.** Pi Pocket asks the sandboxed sessions it knows (`Sandboxes.folders`): a folder counts when a sandboxed session works in it, in a folder that holds it, or in one inside it, found by walking the folder's path from `/` one name at a time: links are followed only while the walk is outside every sandboxed folder, and the walk is inside as soon as it reaches one, known by the device and inode of that folder, not by a path (so an alias, a link into the middle of the project, or a mount of the same folder finds it, and a guest that makes a folder of the project a link to another place does not take it out of the project's reach). A session whose folder lies in a sandboxed folder is then reached from that folder, name by name, so that a link on the way fails the call, and so a folder that a sandboxed and an ordinary session share is confined for both (the guest writes it all the same). In a folder that only ordinary sessions use, Pi has the whole machine anyway: links, such as an `AGENTS.md` that points to a shared file, work as before, and so does git with its filters. A path that someone types outside the folder is theirs to read. Pi Pocket's own git (Changes, branches, the file list) is told which repository to use in every folder, never finds one by itself (`safe.bareRepository=explicit`), and, **in the folder of a sandboxed session**, runs none of the clean, smudge, and process filters that the configuration defines, whatever a `.gitattributes` there says: in a repository that uses Git LFS, Changes then shows the pointers, not the files they stand for (`src/server/git.ts`). What git itself reads or writes in the work tree by path (the status and diffs of Changes, `git worktree add`) is git's own: it does not run the guest's programs, and Undo in Changes does not use it for the work tree here.
- **The network** you choose: **Allow list** (the default: package registries and GitHub, which you can edit), **Open** (public hosts), or **Off**. The VM never reaches this machine's `localhost` or your local network. Only HTTP and HTTPS leave it.

## The browser

The `browser` tool and the Browser panel of a sandboxed session use Chromium **inside the VM**. They never use this machine's browser. The browser:

- opens a file of the shared folder at its path (`file:///…`);
- opens a server that Pi starts in the VM, at `localhost:<port>` (inside the VM);
- is subject to the sandbox's network rules: a page cannot reach this machine's servers or your local network, and under Allow list reaches only the allowed hosts;
- shows in the Browser panel as usual (a screencast over the app's own connection). Pi Pocket opens **no port** on this machine for it: the browser's DevTools pipe runs over the VM's command channel.

It needs the image with a browser (**Set up with a browser**, then **Guest image: With browser**). Without it the tool says so, and the panel shows the reason. **Browser in sandboxed sessions: Off** turns it off. The cost of the browser: a larger image (+280 MB download, +860 MB on disk), about 0.3 s more to start a VM, 1.2 s for the first page, and about 200 MB of memory more in the VM while a page is open.

## Lifecycle and limits

- One VM for each session (its subagents share it). It starts at the first call that needs it, never at module load, and takes about half a second.
- It stops when idle (30 minutes by default), when the session is archived or removed, when you turn the session's sandbox off, when the module goes off, and when the server stops. Things the VM made outside the folder go with it. Processes in it end. A stop, or turning the sandbox off, finishes only when the VM is really gone: a start that is under way is waited for, and a second stop waits for the first. When you turn the sandbox off, no call of the session can start a VM again; if the VM cannot be closed, the sandbox **stays on**, with the reason, and turning it off again tries once more. A VM counts as closed only when its runner process is shown gone: a runner that outlives a failed close is killed with its process group, and one that cannot be shown gone keeps the close failing. When the module goes off, its provider stays until every VM is closed; a VM that cannot be closed keeps its session on, with the reason, even though the module is gone, and every turn-off of a session ends the runners that an earlier module version left for it (or fails).
- Each VM has CPUs (2), memory (2 GB), a root disk (4 GB), and the owner's **Sandboxes at once** limit (default 3, from 1 to 16). When it is full, a call that needs another VM fails with a message that names the sessions that hold VMs and how to free one: the owner stops an idle VM with **Stop** in the sandbox sheet (**Running sandboxes**), or raises the limit.
- **Turning the sandbox on or off is one step at a time, and no tool call of the session runs meanwhile** (it waits, then runs under the setting that the step leaves; so do a goal's check and a launch of the browser from the Browser panel, which refuses when the step turned the sandbox off). Turning it **on** looks for work that still runs on this machine first (a `bash` or file call, a `background` call that has not made its record yet, a `browser` call, any tool call but the ones that touch only Pi Pocket's own state, a `!` command, a goal's check, a background task), and stores the setting only when there is none: a refused turn-on never has a VM. Turning it **off** stops the VM and what runs in it, waits until it is gone, and only then stores the setting: until then the folder is still treated as a sandboxed one (links and git filters, [above](#what-the-vm-sees)). A VM that cannot be stopped keeps the sandbox on, with the reason.
- **Stricter rules end the VM.** When the owner turns the network off, shortens the allow list, or makes the folder read only, the VMs that run with the old rules stop at once (a call that ran in one ends as interrupted). Looser rules wait for the next start: the sheet shows each VM's own rules, and says when they are older than the settings.
- **A session that moves to another folder** gets a new VM at its next call (a call made for the old folder fails, and says so): the old VM mounts the old folder, so it ends, with a task or a browser that held it (Pi is told that the task ended).
- A VM whose runner dies (a crash, a kill) is dropped at once: its slot is free, its tasks end, and the next call starts a new one.
- A restart of the server ends the VMs. A tool call that it cut off comes back as **interrupted** and does not run again. The next call starts a new VM. A runner that a crash left behind is ended at the next start.

## When it cannot start

A call that needs a VM that cannot start **fails, with the reason**, in the tool result and the transcript: "The sandbox could not start: …". It never runs on this machine instead. With the module off, a sandboxed session runs nothing either: the owner turns the module on, or turns the session's sandbox off.

The sheet's **This machine** list says what is missing, and **Check again** looks again:

| Platform            | Works                                                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Linux x86-64        | Yes. libkrun (prebuilt, needs read and write access to `/dev/kvm`) or QEMU. Tested for real with libkrun.                        |
| Linux arm64         | QEMU only (`qemu-system-aarch64`, with KVM). Not tested.                                                                         |
| macOS, Windows      | No, for now. The guarantee is kept only where it can be enforced. Run Pi Pocket on Linux (WSL 2 counts, when it has `/dev/kvm`). |
| A container or a VM | Only when it has `/dev/kvm`.                                                                                                     |

Pi Pocket never installs system packages. **Remove the package and images** in the sheet deletes the `gondolin` folder.

## What it protects, and what it does not

It protects the rest of the machine from what Pi runs: Pi's sign-ins, Pi Pocket's data and token, SSH keys, other sessions' folders, and the local network. It does **not** protect:

- **The shared folder.** Pi reads every file in it (a `.env` too) and, when it is read and write, changes them. A backdoor that Pi writes into your source is still a backdoor.
- **Against a bug in Gondolin, libkrun, QEMU, or the guest kernel.** The VM's file bridge and network proxy run inside the Pi Pocket server process, in TypeScript.
- **Programs that your own global or system git configuration runs by a relative path.** A global `core.fsmonitor = ./watch.sh`, for example, runs the project's own `watch.sh` in every repository, and the VM can rewrite that file. That is your choice, like running a project's scripts, and Pi Pocket does not read command strings to find it: only the repository's own configuration is held to plain data (above).
- **Tools that stay on the host**, if you allow them.
- **Data that leaves through an allowed host.** Open mode lets it leave to any public host.
- **People.** Anyone who can steer a session can still make Pi do what the session allows. The sandbox limits Pi, not people.

See [SECURITY.md](../SECURITY.md) and the design (`docs/design/gondolin-sandbox.md` in the repository).

## Known issues

- **Gondolin 0.14's own image build.** `gondolin build` makes a libkrun image that does not boot on x86-64 Linux ("Kernel doesn't fit in RAM"). Set up with a browser works around it: it builds only the root disk and puts it into the published image's directory, whose kernel boots. The standard image is the published one, unchanged.
- **`rg` and compilers are not in the images.** `git` is, when Set up could build it.
- Output of a command that is cut at its limits is not kept whole in a file (the spill file of `bash` is not available in the VM).
- The sandbox does not report file changes to Pi (`watch` is not supported); Pi Pocket does not need it.
- **Prompt templates and other files outside the folder** are not in the VM (skills are, read only). `AGENTS.md` files are read by Pi Pocket and sit in the prompt, so they work.
- **A skill added after the VM started** is read at the next start (stop the VM from the sheet).
- A file larger than 64 MB cannot be opened by the `read` tool in the VM (use `bash`).
